# 成果物ルール

## 1. 目的

成果物の配置、命名、形式、文字コードを統一し、後続フェーズで迷わず参照できる状態にします。

## 2. 推奨フォルダー構成

```text
Redmine8842/
  00_概要ルール/
  01_要求受付
  02_調査/
  03_影響分析/
  04_設計/
    論理設計/
    物理設計/
  05_実装計画/
  06_コード変更/
  07_テスト/
    テストケース/
    テストデータ/
    SQL確認/
  08_証跡/
    画面証跡/
    SQL結果/
    ログ/
  09_最終レビュー/
  99_アーカイブ/
```

## 3. 命名規則

基本形式:

```text
<チケット番号>_<フェーズ番号>_<成果物名>.<拡張子>
```

例:

```text
8842_01_要求サマリー.md
8842_02_調査結果.md
8842_02_影響ソース一覧.md
8842_02_関連DBオブジェクト一覧.md
8842_03_影響分析.md
8842_03_リスク一覧.md
8842_04_論理設計.md
8842_04_物理設計.md
8842_05_実装計画.md
8842_07_テストケース.md
8842_07_テストデータ.sql
8842_08_証跡サマリー.md
8842_09_最終レビュー.md
```

## 4. ファイル形式

| 種別 | 拡張子 | 保存先 | 備考 |
|---|---|---|---|
| 要求・設計・報告 | `.md` | 各フェーズフォルダー | Markdownを基本とする。 |
| SQL確認 | `.sql` | `07_テスト/SQL確認/` または `08_証跡/SQL結果/` | 目的、前提、確認SQL、期待結果をコメントで記載する。 |
| テストデータ | `.sql` / `.xlsx` | `07_テスト/テストデータ/` | セットアップ、期待値、クリーンアップを分離する。 |
| 画面証跡 | `.png` / `.jpg` | `08_証跡/画面証跡/` | テストケースIDをファイル名に含める。 |
| 実行ログ | `.txt` / `.log` | `08_証跡/ログ/` | 実行日時、環境、コマンドを記録する。 |

## 5. 文字コード

- 新規Markdownは原則UTF-8で保存します。
- 日本語ファイル名は使用可能ですが、役割が分かる命名にします。
- 新規の成果物名、フォルダー名、参照パスは原則として日本語で統一します。
- 既存ファイル名が英語の場合、後続フェーズで参照する前に日本語名へ置換するか、置換できない理由を記録します。
- 既存ファイルを更新する場合は、文字化けを避けるため既存文字コードを確認します。
- 文字化けを発見した場合は、修正前に対象ファイルと状況を記録します。

## 6. Markdown記述ルール

- 見出しは `#`, `##`, `###` を使用します。
- 表は、要求、対象ファイル、対象メソッド、テストケース、証跡の管理に使用します。
- 推測は「前提」または「仮定」として明記します。
- 決定事項と未確認事項を混在させません。

## 7. SQL記述ルール

SQL確認ファイルには、可能な限り以下を含めます。

```sql
-- 目的:
-- 対象テストケース:
-- 前提データ:
-- 確認観点:
-- 期待結果:
```

- 実DBへ反映するSQLと確認専用SQLを分けます。
- テスト用SQLは原則 `BEGIN TRANSACTION` と `ROLLBACK TRANSACTION` を使用します。
- 本番相当環境で実行する場合は、環境ルールに従います。

## 8. 成果物レビュー観点

- ファイル名からチケット番号、フェーズ、用途が分かる。
- 参照元と根拠が記載されている。
- 後続フェーズで利用できる情報量がある。
- 同じ内容が複数ファイルで矛盾していない。
- 不要な一時ファイルが成果物フォルダーに混在していない。
