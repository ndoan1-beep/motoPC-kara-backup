# 8842_03_影響分析

最新更新時刻：　2026年08月20日13:04:16

## 1. 目的

Redmine 8842 の要求に対し、売変・廃棄伝票取消時に元伝票を論理削除しない変更を行う場合の影響範囲、変更候補、維持すべき既存動作、後続設計で扱う論点を整理する。

## 4. 確認済み現行動作

| 区分 | 確認済み内容 | 影響 |
|---|---|---|
| UI | 取消時に `CancelMode = Constants.OnFlag` を設定し、Facadeの `UpInsSARSlipNew(...)` を呼び出す。 | 取消要求の入口。原則維持する。 |
| Facade | `SalesChangeDisposalSlipEntryNewFacade.UpInsSARSlipNew(...)` がBusinessの `UpInsSlipNew(...)` を呼び出す。 | 呼出経路は維持候補。 |
| Business | `CancelMode == Constants.OnFlag` の場合、`SlipUpdateMode = slipUpdateMode_Red` を設定する。 | 赤伝登録へ進むため維持が必要。 |
| Business | 取消時に `UpdateDelFlgSARSlipHeaderNew` / `UpdateDelFlgSARSlipDetailNew` を呼び出す。 | 通常伝票の論理削除抑止対象。 |
| Business | ErrorTable経路で `UpdateDelFlgSARSlipHeaderErrorNew` / `UpdateDelFlgSARSlipDetailErrorNew` を呼び出す。 | Error系伝票の扱いを設計で確定する必要がある。 |
| DataAccess | 4つの `UpdateDelFlg...New` メソッドが `LogicalDelFlg = '1'`, `LogicalDelDate`, `UpdateBy`, `UpdateDate` を更新する。 | Redmine 8842 の中心変更箇所。 |
| 赤伝登録 | `slipUpdateMode_Red` の場合、`UpInsSlipExecuteForDenyNew` で赤伝登録する。 | 変更後も維持する。 |
| 伝票検索 | `SARSlipHeader` と `SARSlipHeaderError` を `UNION` するDataSetを使用する。 | 元伝票と赤伝の検索可否に影響。 |
| 訂正不可制御 | 在庫月度条件または `SlipCorrectionAvailabilityFlg == "0"` の場合に修正ボタンを非表示にする。 | 元伝票・赤伝の訂正不可条件追加候補。 |
| 大福帳 | `DataId "03"` / `"04"` を使用し、赤伝大福帳では `CorrectionDiv = "-"` と符号反転を行う。 | 大福帳連携は維持対象。 |

## 5. 影響分析サマリー

| 領域 | 影響度 | 変更要否 | 分析結果 |
|---|---|---|---|
| UI | Medium | 追加確認あり | 取消入口は維持する。検索結果の修正ボタン非表示条件は元伝票・赤伝に対して追加制御が必要。 |
| Facade | Low | 原則不要 | 現行ではBusinessへの中継であり、要求上の主要変更点ではない。 |
| Business | High | 必要 | 取消時の論理削除呼出を抑止または条件分岐し、赤伝登録経路は維持する必要がある。 |
| DataAccess | High | 条件次第 | `UpdateDelFlg...New` 自体を変更するより、Business側で呼出条件を限定する案が影響を局所化しやすい。 |
| DB | High | スキーマ変更は未判断 | 既存テーブル項目で実現できる可能性があるが、実スキーマ未確認のため設計で再確認が必要。 |
| 伝票検索 | High | 必要 | 元伝票を論理削除しない場合、検索結果に残る一方、赤伝との重複表示と訂正不可制御の整合が必要。 |
| 大福帳連携 | High | 維持が必要 | 論理削除抑止により赤伝大福帳登録や `DataId "03"` / `"04"` の経路を止めないことが重要。 |
| テスト | High | 必要 | DB更新、赤伝登録、検索、訂正不可、大福帳連携、他伝票回帰を確認する必要がある。 |

## 6. 主要変更候補

| ID | 変更候補 | 対象 | 目的 | 影響 |
|---|---|---|---|---|
| CHG-8842-03-001 | 売変・廃棄取消時のみ、通常伝票の論理削除呼出を抑止する。 | `SalesChangeDisposalSlipEntryNewBusiness.cs` | 元伝票を削除扱いにしない。 | 検索表示、訂正不可制御、既存取消済み扱いに影響。 |
| CHG-8842-03-002 | ErrorTable経路の論理削除呼出も同じ方針で扱うか設計判断する。 | `SalesChangeDisposalSlipEntryNewBusiness.cs` | Error系伝票の要求対象を明確化する。 | Error系検索、再取込、修正可否に影響。 |
| CHG-8842-03-003 | `slipUpdateMode_Red` と `UpInsSlipExecuteForDenyNew` の呼出は維持する。 | Business | 赤伝登録を維持する。 | 大福帳、相殺、検索結果に影響。 |
| CHG-8842-03-004 | 元伝票・赤伝の訂正不可判定を `SlipCorrectionAvailabilityFlg` 生成元または検索結果加工で追加する。 | Search Business / DataSet / UI | 修正ボタン非表示と訂正不可を実現する。 | 画面表示、直接遷移制御に影響。 |
| CHG-8842-03-005 | 大福帳登録処理は現行呼出順を維持し、変更対象から外す。 | `UpInsAccountBookNew` 周辺 | 在庫サブシステム連携を維持する。 | 連携回帰が必要。 |

## 7. 通常テーブルとErrorテーブルの扱い

| 区分 | 対象 | 現行 | 影響分析 |
|---|---|---|---|
| 通常テーブル | `SARSlipHeader` / `SARSlipDetail` | 取消時に `LogicalDelFlg = '1'` を更新。 | Redmine 8842 の中心対象。元伝票を検索可能にするため、論理削除抑止が必要。 |
| Errorテーブル | `SARSlipHeaderError` / `SARSlipDetailError` | ErrorTable経路で `LogicalDelFlg = '1'` を更新。 | 要求上の対象に含めるか未確定。通常テーブルと整合するなら同方針が候補だが、エラー伝票運用への影響確認が必要。 |

## 8. 設計論点

| ID | 論点 | 設計で決めること |
|---|---|---|
| DSG-8842-03-001 | 論理削除抑止の分岐位置 | Business側で `UpdateDelFlg...New` 呼出を抑止するか、DataAccess側SQLに条件を入れるか。 |
| DSG-8842-03-002 | 対象伝票の判定条件 | 売変・廃棄取消だけに限定する条件として、伝票種別、取消モード、SlipUpdateModeのどれを使うか。 |
| DSG-8842-03-003 | Errorテーブル対象範囲 | Error系の論理削除抑止を通常系と同じ扱いにするか。 |
| DSG-8842-03-004 | 相殺の期待値 | 赤伝登録による相殺で足りるか、元伝票側の数量・金額更新も必要か。 |
| DSG-8842-03-005 | 訂正不可の実装位置 | `SlipCorrectionAvailabilityFlg` 生成元、検索結果加工、UI制御、Business側遷移制御のどこで担保するか。 |
| DSG-8842-03-006 | 大福帳維持 | 論理削除抑止後も `DataId "03"` / `"04"` と赤伝大福帳登録が同じタイミングで実行されること。 |

## 9. 後続フェーズ判断

フェーズ4設計へ進める。ただし、次の未確認事項は設計時の前提または確認待ち事項として扱う。

- 数量・金額相殺の対象項目、符号、期待値。
- `FillBySlipHeaderListSearchCondition` の最終WHERE条件、特に `LogicalDelFlg` 条件。
- `SlipCorrectionAvailabilityFlg` の生成元とサーバー側訂正不可制御の要否。
- `DataId "03"` が対象環境で `SAR003` に解決されること。
- `SARSlipHeader` / `SARSlipDetail` / Error系 / `CMCAccountBook` の実スキーマ。
- 既存取消済みデータの補正要否。
