# 8842_03_変更方針

最新更新時刻：　2026年08月20日13:04:16

## 1. 目的

フェーズ4設計へ引き継ぐため、Redmine 8842 の変更方針候補、維持する既存動作、設計で確定すべき論点を整理する。

## 2. 変更方針サマリー

| ID | 方針 | 判定 | 理由 |
|---|---|---|---|
| POL-8842-03-001 | 論理削除更新は、売変・廃棄取消時のみ抑止する。 | 推奨 | 要求は売変・廃棄取消が対象であり、他伝票への副作用を避けるため。 |
| POL-8842-03-002 | `CancelMode == Constants.OnFlag` による赤伝モード切替は維持する。 | 必須 | 赤伝登録と数量・金額相殺を成立させるため。 |
| POL-8842-03-003 | `UpInsSlipExecuteForDenyNew` の赤伝登録経路は維持する。 | 必須 | 新規登録赤伝を作成する要求に直結するため。 |
| POL-8842-03-004 | `UpdateDelFlg...New` メソッド本体より、Business側の呼出抑止または条件分岐を優先検討する。 | 推奨 | DataAccess SQLの既存利用箇所への副作用を局所化しやすいため。 |
| POL-8842-03-005 | 伝票検索の訂正不可は、画面表示制御だけでなくサーバー側制御要否も設計で確認する。 | 必須 | 修正ボタン非表示だけでは直接遷移を防げない可能性があるため。 |
| POL-8842-03-006 | 大福帳連携は既存呼出順を維持する。 | 必須 | 在庫サブシステム連携維持が要求されているため。 |

## 3. 推奨する実装分割案

### 3.1 論理削除抑止

| 項目 | 方針候補 |
|---|---|
| 分岐位置 | `SalesChangeDisposalSlipEntryNewBusiness.cs` の取消判定内で、Redmine 8842 対象時のみ `UpdateDelFlg...New` 呼出を抑止する。 |
| 対象 | `SARSlipHeader` / `SARSlipDetail` を優先対象とする。 |
| Error系 | `SARSlipHeaderError` / `SARSlipDetailError` は業務上の取消対象に含めるか設計で判断する。通常系と同じ扱いにする場合は同様に呼出抑止する。 |
| DataAccess | `UpdateDelFlg...New` メソッドは既存用途が残る可能性があるため、削除せず維持する。 |

### 3.2 赤伝登録維持

| 項目 | 方針候補 |
|---|---|
| 赤伝モード | `CancelMode == Constants.OnFlag` 時の `SlipUpdateMode = slipUpdateMode_Red` は維持する。 |
| 登録処理 | `slipUpdateMode_Red` の `UpInsSlipExecuteForDenyNew` 呼出は維持する。 |
| トランザクション | 現行の登録・大福帳処理のトランザクション境界を変更しない方針で設計する。 |

### 3.3 数量・金額相殺

| 項目 | 方針候補 |
|---|---|
| 基本方針 | 赤伝登録によるマイナスまたは反転データで相殺する前提を第一候補とする。 |
| 確認項目 | `TotalQty`, `SlipOldTotalPrice`, `SlipNewTotalPrice`, `SlipTotalDisposalAmt`, `DisposalChangeQty`, `SalesChangePrice`, `DisposalPriceAmt`。 |
| 未確定事項 | 符号、更新先、端数、売変と廃棄の差異、ヘッダー合計と明細合計の整合。 |

### 3.4 伝票検索・訂正不可

| 項目 | 方針候補 |
|---|---|
| 検索表示 | 元伝票は論理削除しないことで検索対象に残す。赤伝は現行赤伝登録結果を検索対象にする。 |
| 検索SQL | `SlipHeaderListDataSet.xsd` と生成SQLの `LogicalDelFlg` 条件を確認する。 |
| 訂正不可 | 元伝票・赤伝に対して `SlipCorrectionAvailabilityFlg == "0"` 相当を返す設計を検討する。 |
| UI制御 | 現行の修正ボタン非表示制御を活用する。 |
| サーバー制御 | `GridView_ItemCommand` または訂正画面入口で対象伝票の訂正不可を再判定する案を検討する。 |

### 3.5 大福帳連携

| 項目 | 方針候補 |
|---|---|
| 基本方針 | `UpInsAccountBookNew`、`GenerateRedAccountBookDataSetNew`、`RegisterAccountBookForJournal` の既存経路を維持する。 |
| 売変 | `DataId "03"` または `"02"` の判定を維持する。 |
| 廃棄 | `DataId "04"` と、廃棄時の売変DataID `"03"` 側赤伝作成経路を維持する。 |
| 赤伝 | `CorrectionDiv = "-"` と符号反転処理を維持する。 |
| 確認事項 | `"03"` が対象環境で `SAR003` に解決されること。 |

## 4. 採用しない方針候補

| 方針 | 採用しない理由 |
|---|---|
| `UpdateDelFlg...New` メソッドを削除する | 他用途が残る可能性があり、影響が大きい。 |
| `CancelMode` 分岐全体を止める | 赤伝登録、大福帳登録まで止まる可能性がある。 |
| UIの修正ボタン非表示だけで訂正不可とする | 直接遷移や別経路からの訂正を防げない可能性がある。 |
| 大福帳処理を再設計する | 要求は既存連携維持であり、変更範囲を広げる必要がない。 |
| DBスキーマ変更を前提にする | 実スキーマ未確認であり、既存項目で実現できる可能性がある。 |

## 5. フェーズ4設計への引き継ぎ

| ID | 引き継ぎ内容 | 優先度 |
|---|---|---|
| NEXT-8842-03-001 | 売変・廃棄取消だけを対象に論理削除呼出を抑止する分岐条件を設計する。 | High |
| NEXT-8842-03-002 | ErrorTable経路を要求対象に含めるか判断し、含める場合は通常系と同じ設計にする。 | High |
| NEXT-8842-03-003 | 元伝票・赤伝の訂正不可判定を、検索結果とサーバー側制御の両面で設計する。 | High |
| NEXT-8842-03-004 | 数量・金額相殺の期待値、符号、対象項目を設計する。 | High |
| NEXT-8842-03-005 | 大福帳連携の既存呼出順とDataIDを変更しない設計にする。 | High |
| NEXT-8842-03-006 | DB接続可能後に実スキーマ、検索SQL、既存データ補正要否を確認する。 | Medium |

## 6. 初期判断

フェーズ4設計へ進める。ただし、数量・金額相殺の期待値、`SlipCorrectionAvailabilityFlg` の生成元、`DataId "03"` と `SAR003` の対応、DB実スキーマは未確認のため、設計成果物では「確認済み事実」と「仮定」を分けて記載する必要がある。
