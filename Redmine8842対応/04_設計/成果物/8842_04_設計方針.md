# 8842_04_設計方針

最新更新時刻：　2026年08月26日09:36:35

## 1. 目的

Redmine 8842 の要求に対し、売変・廃棄伝票取消時に元伝票を論理削除せず、赤伝登録、数量・金額相殺、伝票検索画面での訂正不可制御、大福帳連携維持を実現するための設計方針を定義する。

## 3. 設計方針サマリー

| ID | 方針 | 内容 |
|---|---|---|
| POL-8842-04-001 | 論理削除抑止 | 売変・廃棄の伝票取消時、元伝票に対する `LogicalDelFlg = '1'`、`LogicalDelDate` の更新を実行しない。 |
| POL-8842-04-002 | 赤伝登録維持 | `CancelMode == Constants.OnFlag` の場合に `SlipUpdateMode = slipUpdateMode_Red` を設定し、`UpInsSlipExecuteForDenyNew` による赤伝登録は維持する。 |
| POL-8842-04-003 | 処理順維持 | 論理削除更新だけをスキップし、赤伝登録、大福帳登録、既存トランザクション境界は現行構造を崩さない。 |
| POL-8842-04-004 | 変更局所化 | `UpdateDelFlg...New` メソッド本体は削除せず、Business層の呼出条件でRedmine 8842対象時のみ抑止する案を採用候補とする。 |
| POL-8842-04-005 | 訂正不可制御 | 検索結果の `SlipCorrectionAvailabilityFlg` を活用し、画面の修正ボタン非表示に加えて直接遷移時のサーバー側再判定を設計対象にする。 |
| POL-8842-04-006 | 大福帳維持 | `DataId "03"` / `"04"`、`GenerateRedAccountBookDataSetNew`、`RegisterAccountBookForJournal` の既存経路を維持する。 |
| POL-8842-04-007 | DB構造未確認の扱い | DB接続不可、かつ `query_database_structure` 未公開のため、DB構造はDataAccess SQL、DataSet定義、`query_database_architecture` を暫定根拠とする。 |

## 4. 変更対象と維持対象

| 区分 | 対象 | 設計方針 |
|---|---|---|
| 変更 | `SalesChangeDisposalSlipEntryNewBusiness.cs` の取消分岐 | 元伝票論理削除呼出のみ抑止する分岐を追加する。 |
| 変更 | 伝票検索結果生成または検索結果加工 | 元伝票と赤伝を訂正不可にする判定を追加する。 |
| 変更 | 検索結果画面の訂正遷移 | 直接遷移時にも訂正不可を再判定する。 |
| 維持 | UI取消入口 | `CancelMode = Constants.OnFlag` を維持する。 |
| 維持 | Facade呼出 | `UpInsSARSlipNew(...)` からBusinessへ渡す経路を維持する。 |
| 維持 | 赤伝登録 | `SlipUpdateMode = slipUpdateMode_Red` と `UpInsSlipExecuteForDenyNew` を維持する。 |
| 維持 | DataAccess論理削除メソッド | 既存用途保護のため削除しない。 |
| 維持 | 大福帳登録 | DataID判定、赤伝大福帳生成、登録呼出を維持する。 |

## 5. 採用方針

| 項目 | 採用内容 | 理由 |
|---|---|---|
| 論理削除抑止位置 | Business層の取消分岐 | DataAccess SQL本体を変更せず、影響を売変・廃棄取消に限定しやすい。 |
| Error系 | 通常系と同じ候補として設計するが、最終適用は未確認事項とする | ErrorTable経路にも論理削除呼出があるため、通常系と不整合にしないため。 |
| 数量・金額相殺 | 赤伝登録による相殺を第一候補とする | 現行で赤伝登録と赤伝大福帳生成が存在するため。 |
| 訂正不可 | `SlipCorrectionAvailabilityFlg == "0"` 相当の制御を追加候補にする | 現行の修正ボタン非表示条件を活用できるため。 |
| 大福帳 | 既存経路を変更しない | 要求が連携維持であり、新規再設計は不要なため。 |

## 6. 採用しない方針

| 方針 | 不採用理由 |
|---|---|
| `CancelMode` 分岐全体を削除する | 赤伝登録まで止まる可能性がある。 |
| `UpdateDelFlg...New` メソッドを削除する | 他用途への影響が不明であり、影響範囲が大きい。 |
| UIの修正ボタン非表示だけで訂正不可とする | 直接遷移や別経路からの訂正を防げない可能性がある。 |
| DBスキーマ変更を前提にする | 実スキーマ未確認であり、既存項目で実現できる可能性がある。 |
| 大福帳処理を作り替える | 要求は既存連携維持であり、変更範囲を広げる必要がない。 |

## 7. 後続フェーズへの引き継ぎ

フェーズ5実装計画では、以下をタスク分解する。

- Business層での論理削除呼出抑止。
- Error系論理削除抑止の適用有無。
- 検索結果における元伝票・赤伝の訂正不可フラグ設定。
- 訂正遷移時のサーバー側再判定。
- 赤伝登録、大福帳登録が現行通り実行されることの確認観点。
- DB構造、`SAR003` 実解決、既存取消済みデータ補正要否の確認タスク。
