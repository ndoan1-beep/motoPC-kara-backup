# 8842_04_DB更新設計

最新更新時刻：　2026年08月26日09:36:35

## 1. 目的

売変・廃棄伝票取消時に元伝票を論理削除しないためのDB更新方針、赤伝登録による相殺、大福帳連携維持、DB未確認事項を整理する。

## 2. DB確認前提

| 項目 | 内容 |
|---|---|
| DB接続 | 直接接続不可 |
| MCP DB確認 | `query_database_architecture` のみ利用実績あり。`query_database_structure` は未公開。 |
| 根拠 | DataAccess SQL、DataSet定義、フェーズ2/3成果物 |
| 実スキーマ | 未確認。後続でDB接続または構造取得ツールにより確認する。 |

## 3. 論理削除更新設計

| テーブル | 現行更新 | 変更後 |
|---|---|---|
| `SARSlipHeader` | `LogicalDelFlg = '1'`, `LogicalDelDate`, `UpdateBy`, `UpdateDate` | 売変・廃棄取消時は更新しない。 |
| `SARSlipDetail` | 同上 | 売変・廃棄取消時は更新しない。 |
| `SARSlipHeaderError` | 同上 | Error系を対象に含める場合は更新しない。対象外なら現行維持。 |
| `SARSlipDetailError` | 同上 | Error系を対象に含める場合は更新しない。対象外なら現行維持。 |

`UpdateBy`、`UpdateDate` は論理削除SQL内で同時更新されているため、論理削除呼出を抑止する場合は同時に更新されない。元伝票に取消操作履歴を残す別項目が必要かは未確認事項とする。

## 4. 赤伝登録DB設計

| 対象 | 設計 |
|---|---|
| 赤伝ヘッダー | 現行の `InsertSARSlipHeaderForDenyNew` 相当の登録を維持する。 |
| 赤伝明細 | 現行の `InsertSARSlipDetailForDenyNew` 相当の登録を維持する。 |
| 採番 | 現行赤伝登録処理に従う。採番仕様は後続確認。 |
| 元伝票関連付け | 既存赤伝登録項目を利用する。関連付け項目の明示は後続確認。 |

## 5. 数量・金額相殺DB設計

| 区分 | 対象候補 | 設計 |
|---|---|---|
| ヘッダー数量 | `TotalQty` | 元伝票と赤伝の合計で相殺確認する。 |
| 売変ヘッダー金額 | `SlipOldTotalPrice`, `SlipNewTotalPrice` | 赤伝側の値と符号を確認する。 |
| 廃棄ヘッダー金額 | `SlipTotalDisposalAmt` | 赤伝側の値と符号を確認する。 |
| 明細数量 | `DisposalChangeQty` | 赤伝側の符号または反転値を確認する。 |
| 売変明細金額 | `SalesChangePrice` | `(SlipOldPrice - SlipNewPrice) * DisposalChangeQty` の赤伝側扱いを確認する。 |
| 廃棄明細金額 | `DisposalPriceAmt` | `SlipDisposalUnitPrica * DisposalChangeQty` の赤伝側扱いを確認する。 |

追加の元伝票更新は、業務期待値が確定するまで設計確定しない。

## 6. 検索DB設計

| 対象 | 設計 |
|---|---|
| `SlipHeaderListDataSet.xsd` | `SARSlipHeader` と `SARSlipHeaderError` のUNIONを維持する。 |
| `LogicalDelFlg` 条件 | 最終WHERE条件が未確認。元伝票を表示できない条件がある場合は検索条件変更候補とする。 |
| `SlipCorrectionAvailabilityFlg` | 検索結果列として存在する。元伝票・赤伝は `"0"` 相当を返す方針。 |

## 7. 大福帳DB設計

| 対象 | 設計 |
|---|---|
| `CMCAccountBook` | 既存大福帳登録・更新を維持する。個別DB資産はMCPで未検出。 |
| `CMCDataIDControl` | `DataId "03"` / `"04"` の確認対象。 |
| `CMCAccountBook_SAR001` | 取込/集計/削除系の回帰確認対象。 |
| `SAR003` | `DataId "03"` が実環境で `SAR003` に解決されるか確認する。 |

## 8. DB変更要否

| 変更 | 判定 | 理由 |
|---|---|---|
| DBスキーマ変更 | 不要候補 | 要求は既存論理削除更新の抑止と既存赤伝登録維持であり、新規項目追加は現時点で不要。 |
| 論理削除SQL本体変更 | 原則不要 | Business側呼出抑止で実現するため。 |
| 検索SQL変更 | 要確認 | `LogicalDelFlg` 条件や訂正不可フラグ生成方法次第。 |
| 大福帳SQL変更 | 不要候補 | 既存連携維持が要求であるため。 |
