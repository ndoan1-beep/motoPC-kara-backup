# 8842_02_調査結果

最新更新時刻：　2026年08月18日16:03:47

## 1. 目的

Redmine 8842 の要求に対し、売変・廃棄伝票取消時の現行実装をMCPサーバー `mcp__dotnet_semantic_index` と組み合わせて再調査し、後続の影響分析に必要な現行動作、関連ソース、関連DBオブジェクト、未確認事項を整理する。

今回はDBへ直接接続できないため、DB関連はMCPの `query_database_architecture` で読めるデータ層情報、およびMCPの `read_source_file_range` で読んだDataAccess SQL/DataSet定義を根拠に整理する。

| 区分 | 使用ツール | 結果 |
|---|---|---|
| 索引更新 | `refresh_codebase` | コードベース再索引を実行。 |
| セマンティック検索 | `query_semantic_graph` | UI、Facade、Business、DataAccess、検索画面、検索Business、DataSetを特定。 |

| データ層照会 | `query_database_architecture` | `SARSlipHeader` / `SARSlipDetail` / `SARSlipHeaderError` / `SARSlipDetailError` / `CMCAccountBook` / `SAR003` は個別DB資産として未検出。`SARSlip`、`AccountBook`、`CMCDataIDControl`、`CMCAccountBook_SAR001` では関連ストアドと影響テーブルを確認。 |

## 3. 確認済み事実

### 3.1 取消時の元伝票論理削除

現行実装では、UIで取消モードを設定し、Facade経由でBusinessへ登録処理を渡す。Businessは取消モードを検知すると赤伝モードへ切り替えた上で、元伝票側に削除フラグをセットする。

| 対象 | 確認内容 | MCP根拠 |
|---|---|---|
| UI取消設定 | `workEntity.CancelMode = Constants.OnFlag` を設定 | `Sales/InputSalesSlip/InputSalesSlip.Web/Sales/InputSalesSlip/SalesChangeDisposalSlipInput/SalesChangeDisposalSlipInputUpdate_partial.cs` 1536-1548 |
| UIからFacade | `GetFacadeInstance().UpInsSARSlipNew(...)` を呼び出す | 同 2360-2370 |
| FacadeからBusiness | `UpInsSARSlipNew` がBusinessの `UpInsSlipNew(...)` を呼び出す | `Sales/InputSalesSlip/InputSalesSlip.Facade/SalesChangeDisposalSlipEntryNewFacade.cs` 140-180 |
| Business取消判定 | `CancelMode == Constants.OnFlag` の場合、`SlipUpdateMode = slipUpdateMode_Red` を設定 | `Sales/InputSalesSlip/InputSalesSlip.Business/SalesChangeDisposalSlipEntryNewBusiness.cs` 2174-2210 |
| 通常伝票論理削除 | `UpdateDelFlgSARSlipHeaderNew` / `UpdateDelFlgSARSlipDetailNew` を呼び出す | 同 2174-2210 |
| エラー伝票論理削除 | `UpdateDelFlgSARSlipHeaderErrorNew` / `UpdateDelFlgSARSlipDetailErrorNew` を呼び出す | 同 2448-2515 |

### 3.2 論理削除SQL

`SalesChangeDisposalSlipEntryNewDataAccessComponent.cs` 1140-1375 で、以下の4テーブルに対して同系統の更新SQLを確認した。

| テーブル | 更新項目 | WHEREキー |
|---|---|---|
| `SARSlipHeader` | `LogicalDelFlg = '1'`, `LogicalDelDate`, `UpdateBy`, `UpdateDate` | `CorporationCode`, `SlipDiv`, `SlipTypeCd`, `SlipNo`, `DisposalChangeDate`, `StoreCd` |
| `SARSlipDetail` | 同上 | 同上 |
| `SARSlipHeaderError` | 同上 | 同上 |
| `SARSlipDetailError` | 同上 | 同上 |

Redmine 8842 の中心変更点は、この論理削除更新を止める、または対象条件で分岐する箇所である。

### 3.3 赤伝登録

`SalesChangeDisposalSlipEntryNewBusiness.cs` 2448-2515 で、`SlipUpdateMode` による登録分岐を確認した。

| モード | 現行処理 |
|---|---|
| `slipUpdateMode_Black` | 黒伝登録 |
| `slipUpdateMode_Red` | `UpInsSlipExecuteForDenyNew` による赤伝登録 |
| `slipUpdateMode_RedBlack` | 赤黒両方の登録 |

取消時は `slipUpdateMode_Red` へ切り替わるため、論理削除更新を見直しても赤伝登録経路は維持する必要がある。

### 3.4 数量・金額相殺候補

検索ヘッダーDataSetと検索明細処理から、数量・金額に関係する項目を確認した。

| 区分 | 項目 | 確認内容 |
|---|---|---|
| ヘッダー | `TotalQty` | `SlipHeaderListDataSet.xsd` の検索SQLで取得 |
| ヘッダー | `SlipOldTotalPrice` | 同上 |
| ヘッダー | `SlipNewTotalPrice` | 同上 |
| ヘッダー | `SlipTotalDisposalAmt` | 同上 |
| 明細 | `DisposalChangeQty` | 検索明細処理で数量として扱う |
| 明細 | `SalesChangePrice` | `(SlipOldPrice - SlipNewPrice) * DisposalChangeQty` で算出 |
| 明細 | `DisposalPriceAmt` | `SlipDisposalUnitPrica * DisposalChangeQty` で算出 |

MCP根拠は `SlipHeaderListDataSet.xsd` 15-130、`SalesChangeDisposalSlipSearchBusiness.cs` 574-690。相殺の期待値、符号、更新タイミングは今回の調査だけでは仕様確定できない。

### 3.5 伝票検索画面の訂正不可制御

検索結果画面では、修正ボタン列と行単位の非表示制御を確認した。

| 対象 | 確認内容 | MCP根拠 |
|---|---|---|
| 修正ボタン列 | `SCRCSAR050306002` の1列目が `修正` / `伝票修正` | `InputSalesSlip.Web.PropertyInfo/SalesChangeDisposalSlipSearchResult.cs` 1-25 |
| 非表示条件1 | `DisposalChangeDate(yyyyMM) < stockMonthly` の場合に非表示 | `SalesChangeDisposalSlipSearchResult_partial.cs` 239-263 |
| 非表示条件2 | `SlipCorrectionAvailabilityFlg == "0"` の場合に非表示 | 同上 |
| 訂正遷移 | 選択行キーをセッションへ格納し、条件により `SCRCSAR050202` へ遷移 | 同 389-492 |

元伝票と新規赤伝を検索可能にしつつ訂正不可にするには、`SlipCorrectionAvailabilityFlg` の生成元または検索結果行生成処理での制御が候補となる。

### 3.6 検索SQL

`SalesChangeDisposalSlipSearchBusiness.cs` 378-491 で、検索ヘッダー取得が `SlipHeaderListDataTableAdapter.FillBySlipHeaderListSearchCondition` を呼び出すことを確認した。

`SlipHeaderListDataSet.xsd` 15-130 では、`SARSlipHeader` と `SARSlipHeaderError` を `UNION` し、`TotalQty`、`SlipOldTotalPrice`、`SlipNewTotalPrice`、`SlipTotalDisposalAmt` などを取得している。

`FillBySlipHeaderListSearchCondition` の最終WHERE条件、特に `LogicalDelFlg` 条件は、生成コードまたは実行SQL確認が必要。

### 3.7 大福帳連携

`SalesChangeDisposalSlipEntryNewBusiness.cs` 2658-2992、6197-6265 で大福帳連携を確認した。

| 対象 | 確認内容 |
|---|---|
| 売変DataID | `DataId` `"03"` または `"02"` をコード区分から取得 |
| 廃棄DataID | `DataId` `"04"` をコード区分から取得 |
| 廃棄時の売変大福帳 | `dataID_SalesChange = DataId "03"` を使用し、廃棄時も売変大福帳側に赤伝を作成する経路がある |
| 赤伝大福帳 | `RegisterAccountBookForJournal(GenerateRedAccountBookDataSetNew(...))` を実行 |
| 赤伝データ生成 | `CorrectionDiv = "-"` を設定し、物流/商流区分を反転 |

`query_database_architecture` では `SAR003` 自体は未検出だが、`CMCDataIDControl` と `AccountBook` 関連の照会で、売変大福帳系ストアド `usp_SARAccountBookUptakeSalesChange` と影響テーブル `CMCDataIDControl` が確認できた。`DataId "03"` が環境上 `SAR003` に解決されることは継続確認。
